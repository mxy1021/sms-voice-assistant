## 2. 已确认的细化决策

- 短信沿用 SMS_RECEIVED、PDU、拼接、防混发和防重复；只处理新短信，不为通知接入重写接收模块。
- 两个开关名称为“仅播报验证码”“精简验证码播报”，完全独立、始终可操作、各自持久化。四组合及识别不明确时的处理按[正式需求](requirements.md)第三章；升级保留原配置，新装均开，进程重启恢复，蓝牙配置不丢失。
- 通知接入采用系统监听机制、用户主动授予使用权。允许必要系统绑定服务，不允许借此增加不必要前台常驻或保活。
- 微信默认启用；其他应用由用户选择，应用列表展示名称/图标，未选应用不进入流程。只取实际提供的内容，不推测联系人、正文或聊天历史。
- 下载进度、媒体播放状态、系统服务状态、应用更新及其他非消息通知不播报。具体分类算法仍为 T13。
- 方案 A 已正式确认，不再是 TBD：非抢占式播放 + 优先级队列；各级按接收顺序 FIFO，当前消息正常结束并释放音频资源后立即优先调度 P0，不保存/恢复被抢占普通消息进度。
- 主动停止、关闭总运行开关、断连、实际路由不匹配、永久焦点丢失及必要安全条件立即停止，优先于正常调度；等待队列如何处置仍按相关 TBD 确认。
- 继承临时焦点丢失/恢复、永久丢失取消、音乐降低/恢复、关闭总开关即停、再次开启不复活旧语音。音频焦点恢复不等于消息优先级抢占后的进度恢复。
- 继承方案 B：80 UTF-16代码单元、PCM最多5秒/1MiB、会话总预算8秒。任一超限整条拒绝，不截断、不部分播放、不承诺任意长度。
- 保留原 applicationId、namespace、签名密钥、现有工程/仓库，最小必要权限；生产/Debug隔离、本地处理、不联网不上传、不读短信历史或微信数据库。
- 阶段0～阶段6的正式任务和验收标准已确认，见[开发计划](development-plan.md)。不再保留“正式阶段映射待补录”的当前结论。
- 此前已确认不纳入蓝牙低电量自动提醒，继续保留。
