## 3. 已确认的调度方案 A

1. P0 为现有规则成功识别的验证码短信；普通短信、微信单聊/群聊及所选应用消息均为 P1。不把其他通知中的验证码提升为 P0。
2. P0/P1 各自按接收顺序 FIFO；P0 优先于所有等待中的 P1。
3. 当前消息正常播放，新验证码只进入 P0 等待，不抢占、不暂停普通消息、不保存其播放进度、不在验证码之后恢复被抢占消息。
4. 正常完成后先释放音频资源，再立即检查 P0；P0 空才取 P1，均空则等待。
5. 单一播放、完成/失败/取消后的资源释放和再次触发调度按统一确认文档第7.2节执行；队列处置仍受 T01～T10 的未决边界约束，不据此新增重试、丢弃或持久化策略。

正式示例：微信 A 正在播报，普通短信 B 到达，验证码短信 C 到达；正常顺序为 **A → C → B**。

安全控制优先：主动停止、总运行开关关闭、目标蓝牙断开、实际路由不匹配、永久焦点丢失及其他必要安全条件立即停止，不等待当前消息正常完成。安全停止后的等待队列如何处理仍按对应 TBD 确认。

“不暂停/恢复普通消息”是禁止消息优先级抢占方案；V1.0 临时焦点丢失及恢复、永久丢失取消、停止后不复活等音频机制继续继承。

## 4. 候选生命周期模型与待确认参数

候选模型保留原文，阶段5可调整实现细节，不得改变已确认优先级和方案 A：

```text
RECEIVED → VALIDATED → FILTERED → DEDUPLICATED → QUEUED → PLAYING → COMPLETED
异常：REJECTED / EXPIRED / CANCELLED / FAILED
```

两个逻辑优先级和方案 A 已确认；以上状态名称、实现结构不作为冻结接口。不得从候选状态名推导未经确认的过滤、失败重试或撤回规则。

[决策台账](technical-decisions.md) T01～T10 覆盖容量、有效期、满队列、淘汰、去重窗口、通知更新/撤销、断连/撤权队列处置及正文临时持久化。容量5条、过期30秒均不是已定数值。

## 5. V1.0 音频、预算与后台继承

复用基线链：SMS/PDU 与规则 → 指定蓝牙连接/预期路由 → 严格离线中文 TTS → 内存 PCM → MAY_DUCK 焦点 → AudioTrack 静音验证实际路由 → PCM 播放 → 释放。现有主要入口/协调/会话为 SmsReceiver、SmsCoordinator、SpeechSession，V2.0 不据此新增或冻结类划分。

- 指定设备必须已连接、有效蓝牙输出存在、身份可确认、实际路由符合预期。任一不满足则拒绝或立即停止，不走手机扬声器、其他蓝牙设备或未知路由。
- 继承离线中文 TTS、PCM、临时焦点丢失/恢复、永久丢失取消、音乐降低/恢复、总开关立即停止、重新开启不复活旧语音。
- 继承方案 B：最多80个 UTF-16 代码单元、PCM 最多5秒/1MiB、会话总预算8秒；任一超限整条拒绝，不截断、不部分播放，不承诺任意长度全文。
- 现有接收起预算、700ms 路由/清理余量、120秒 PDU 有效期和1200ms SMS 焦点窗口保持 V1.0 事实。阶段5须记录排队等待与原生命周期预算的衔接及验证，不擅自重置原预算起点，不将统一消息有效期 T02 自动设为上述任一数值。
- 音乐降低及恢复应分别有系统焦点证据和真实听感，回调不代替耳机听感或无手机语音确认。
- 保留事件驱动架构，不自建24小时常驻前台 Service，不作不必要后台轮询，不通过额外常驻进程规避系统管理。
- 系统绑定 NotificationListenerService 允许作为必要组件验证；Home/锁屏/后台及时性和系统限制必须在阶段2目标 vivo 真机实测，不能由 V1.0 的成功直接推定。
