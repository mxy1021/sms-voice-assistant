# 一、V2.0 产品目标

V2.0 在 V1.0 短信语音播报功能的基础上，增加微信及其他应用的通知语音播报能力。

最终实现一个统一的消息语音助手：

1. 接收手机短信。
2. 识别验证码短信及普通短信。
3. 根据用户设置决定短信播报方式。
4. 接收微信通知并提取可读消息内容。
5. 用户自主选择其他需要播报通知的应用。
6. 统一管理不同来源的消息。
7. 验证码消息拥有最高等待队列优先级。
8. 所有消息通过指定蓝牙耳机播报。
9. 保留离线中文 TTS、音频焦点管理和音乐自动降低及恢复能力。
10. 所有消息在本地处理，不联网、不上传消息内容。

V2.0 的核心方向是：从单一短信验证码播报工具升级为多应用消息语音播报工具。

# 二、消息接入方式

## 2.1 短信接入

**状态：已确认**

继续使用 V1.0 已经正式验收的短信接收架构。

技术方案：

- 使用现有 SMS_RECEIVED 广播接收机制。
- 保留原有 PDU 解析。
- 保留多段短信处理能力。
- 保留短信拼接、防混发及防重复机制。
- 只处理新接收的短信。
- 不读取短信收件箱历史记录。

不得为了接入微信通知而重写 V1.0 的短信接收模块。

## 2.2 微信通知接入

**状态：产品需求已确认，技术方案待真机验证**

微信通知通过 Android 系统通知监听机制接入。

技术候选方案：

`NotificationListenerService`

要求：

1. 用户主动授予通知使用权。
2. 监听微信产生的新通知。
3. 获取系统通知实际提供的应用名称、联系人或群聊名称及正文。
4. 将可读消息转换为统一消息对象。
5. 交由后续消息处理模块。
6. 不读取微信内部数据库。
7. 不通过其他非公开方式获取微信聊天记录。
8. 不联网、不上传通知正文。

特别说明：

NotificationListenerService 是 Android 系统管理绑定的 Service，与 APP 自行启动前台 Service 保活不同。

允许为通知监听实现所必需的系统绑定服务，但不得借此增加不必要的前台常驻 Service 或后台保活机制。

具体后台运行表现、通知接收及时性和系统限制必须在阶段2进行目标 vivo 真机验证。

## 2.3 其他应用通知接入

**状态：产品需求已确认，具体实现待验证**

用户可以选择本机安装的其他应用。

功能要求：

1. 获取本机已安装应用列表。
2. 展示应用名称及图标。
3. 用户可以自主选择需要播报的应用。
4. 微信作为默认通知播报应用。
5. 选定应用后，播报该应用所有可读的消息类通知。
6. 自动过滤非消息通知。
7. 未选定的应用不进入播报流程。

技术候选：

- Android PackageManager。
- Android Package Visibility。
- NotificationListenerService。
- 用户选择的应用包名持久化。

实际需要申请的应用可见性权限，以 Android 版本和技术验证结果为准，不得无必要扩大权限范围。

# 三、短信播报规则

## 3.1 两个独立设置开关

**状态：已正式确认**

主界面保留两个独立开关：

**开关一：仅播报验证码**

作用：控制是否过滤普通短信。

**开关二：精简验证码播报**

作用：控制验证码短信采用精简内容还是原始短信全文。

两个开关完全独立：

- 精简验证码播报不受仅播报验证码开关限制。
- 任意一个开关变化，不得自动修改另一个开关。
- 精简开关始终可以操作。
- 两个开关分别保存状态。

## 3.2 四种规则组合

以下为正式产品规则，不得改变。

| 仅播报验证码 | 精简验证码播报 | 验证码短信 | 普通短信 |
|---|---|---|---|
| 开启 | 开启 | 精简播报 | 不播报 |
| 开启 | 关闭 | 全文播报 | 不播报 |
| 关闭 | 开启 | 精简播报 | 全文播报 |
| 关闭 | 关闭 | 全文播报 | 全文播报 |

### 组合 A：两个开关均开启

- 验证码短信：识别并提取验证码，生成精简语音。
- 普通短信：忽略。

### 组合 B：仅播报验证码开启，精简验证码播报关闭

- 验证码短信：完整朗读原始短信正文。
- 普通短信：忽略。

### 组合 C：仅播报验证码关闭，精简验证码播报开启

- 验证码短信：精简播报。
- 普通短信：完整朗读原始短信正文。

### 组合 D：两个开关均关闭

- 验证码短信：完整朗读原始短信正文。
- 普通短信：完整朗读原始短信正文。

## 3.3 验证码识别异常处理

- 仅播报验证码开启时，验证码识别不明确的短信不播报。
- 仅播报验证码关闭时，无法确认是验证码的短信按照普通短信全文播报。
- 不允许因为验证码识别失败而错误提取或生成验证码内容。

## 3.4 配置兼容

- 现有 V1.0 用户升级后保留原有配置。
- 两个开关分别持久化。
- 新安装默认两个开关均开启。
- 进程重启后恢复原设置。
- 不得因为升级 APK 丢失蓝牙耳机配置。

# 四、微信通知播报规则

## 4.1 播报内容

**状态：已正式确认**

微信通知播报格式：

**应用名称 + 联系人/群聊名称 + 通知正文**

例如：

原始通知信息：

- 应用：微信
- 联系人：张三
- 正文：今晚几点出发？

语音播报：

“微信，张三说：今晚几点出发？”

群聊示例：

“微信，项目开发群说：明天上午十点开会。”

以上措辞为格式示例，实际语音表达可以在 UI 和语音体验测试中优化，但必须保留应用名称、联系人或群聊名称、通知正文这三个信息部分。

## 4.2 内容提取规则

1. 优先提取系统通知实际提供的联系人或群聊名称。
2. 提取系统通知实际提供的正文。
3. 不允许推测缺失的联系人或消息内容。
4. 如果通知没有正文，只能按照后续确认的异常处理规则处理。
5. 不读取微信内部数据库。
6. 不获取系统通知没有提供的聊天历史内容。

## 4.3 微信通知范围

- 微信默认启用。
- 只处理微信的消息类通知。
- 过滤非消息通知。
- 处理单聊和群聊消息。
- 对通知内容不完整的情况进行安全处理。

# 五、其他应用通知播报规则

**状态：产品需求已确认，具体格式及过滤算法待验证。**

用户选定其他应用后：

1. 获取该应用的可读通知。
2. 识别通知是否属于消息类通知。
3. 过滤非消息通知。
4. 将有效通知转换为统一消息对象。
5. 交由消息调度系统处理。

典型规则：

| 通知类型 | 是否播报 |
|---|---|
| 微信个人聊天 | 是 |
| 微信群聊 | 是 |
| 选定应用的消息通知 | 是 |
| 下载进度 | 否 |
| 媒体播放状态 | 否 |
| 系统服务状态 | 否 |
| 应用更新提示 | 否 |
| 其他非消息通知 | 否 |

其他应用的具体播报格式，需要根据各应用实际通知结构确定，不得假定所有应用使用相同的通知字段。

# 六、统一消息优先级与调度规则

## 6.1 优先级划分

**状态：已正式确认**

V2.0 使用两个逻辑优先级。

**P0：验证码短信**

包括通过现有验证码识别规则成功识别的验证码短信。

**P1：其他所有消息**

包括：

- 普通短信。
- 微信个人聊天通知。
- 微信群聊通知。
- 其他用户选定应用的消息通知。

## 6.2 队列内部顺序

**状态：已正式确认**

- P0 内部采用 FIFO，按照接收顺序播放。
- P1 内部采用 FIFO，按照接收顺序播放。
- P0 优先于所有等待中的 P1。

## 6.3 正式队列抢占策略：方案 A

**状态：已正式确认，不再是 TBD。**

采用：

**非抢占式播放 + 优先级队列调度。**

具体规则：

1. 当前正在播放的消息正常播放。
2. 新收到验证码短信时，不立即打断当前消息。
3. 新验证码进入 P0 等待队列。
4. 当前消息必须正常完成播放。
5. 当前消息播放结束后，释放音频资源。
6. 调度器立即检查 P0 队列。
7. P0 队列存在待播报消息时，优先取出最早进入队列的验证码。
8. P0 队列为空时，按照 FIFO 顺序播放 P1 消息。
9. P0 和 P1 均为空时，调度器进入等待状态。

不采用：

- 验证码立即中断正在播放的微信消息。
- 暂停普通消息。
- 保存普通消息播放进度。
- 验证码播报后恢复被暂停的普通消息。

## 6.4 调度示例

假设当前正在播报微信消息 A：

| 时间 | 事件 |
|---|---|
| T1 | 开始播报微信消息 A |
| T2 | 收到普通短信 B，进入 P1 |
| T3 | 收到验证码短信 C，进入 P0 |
| T4 | 微信消息 A 正常播放结束 |
| T5 | 优先播报验证码短信 C |
| T6 | 播报普通短信 B |

最终顺序：

A → C → B。

## 6.5 安全例外

上述正常消息调度规则不限制独立的安全控制。

以下情况仍然必须立即停止当前播报：

- 用户主动停止软件。
- 用户关闭总运行开关。
- 指定蓝牙耳机断开。
- 实际音频路由不匹配。
- 永久音频焦点丢失。
- 其他必须停止音频的安全条件。

安全控制优先于正常队列调度。

# 七、消息队列生命周期设计

## 7.1 建议的消息处理流程

RECEIVED
→ VALIDATED
→ FILTERED
→ DEDUPLICATED
→ QUEUED
→ PLAYING
→ COMPLETED

异常状态：

- REJECTED：消息被规则拒绝。
- EXPIRED：消息超过有效期。
- CANCELLED：消息被取消。
- FAILED：处理或播放失败。

以上是统一消息系统的候选状态模型，具体实现细节可以在阶段5根据实际架构调整，但不得违反已正式确认的优先级和方案 A。

## 7.2 队列调度机制

建议使用两个逻辑队列：

- P0 Queue：验证码短信。
- P1 Queue：普通短信、微信通知和其他应用通知。

调度器规则：

1. 同一时间只允许一个消息进入 PLAYING。
2. 当前消息播放期间，新消息只能进入对应等待队列。
3. 当前消息完成后，优先检查 P0。
4. P0 为空时才检查 P1。
5. P0 和 P1 内部均保持 FIFO。
6. 播报完成、失败或取消后，必须正确释放音频资源。
7. 音频资源释放后重新触发调度。

## 7.3 尚待确认的队列参数

以下内容仍然标记为 TBD：

- 最大队列容量。
- 消息过期时间。
- 队列满时的处理策略。
- 新验证码是否淘汰普通消息。
- 重复通知的去重时间窗口。
- 通知更新后是否重新播报。
- 通知撤销后是否取消待播报任务。
- 蓝牙断开后待播报消息如何处理。
- 通知权限撤销后的队列处理。
- 消息正文是否允许临时持久化。

特别说明：

此前讨论过的队列容量5条、过期时间30秒等数值尚未正式确认，不得直接作为固定产品规则。

必须满足：

- 指定蓝牙设备已连接。
- 存在有效蓝牙音频输出。
- 实际输出路由符合预期。

任一条件不满足：

- 禁止播报或立即停止。
- 不允许手机扬声器回退。
- 不允许输出到其他蓝牙设备。

## 8.3 全文播报预算

继续遵守 V1.0 方案 B：

- 最多80个 UTF-16 代码单元。
- PCM 最多5秒。
- PCM 最大1MiB。
- 会话总预算8秒。

超出任一限制：

- 整条拒绝。
- 不允许截断。
- 不允许部分播报。
- 不允许回退手机扬声器。

任意长度全文播报不属于本次确认范围。

## 8.4 后台运行

继续保留 V1.0 事件驱动架构。

不允许：

- APP 自建24小时常驻前台 Service 保活。
- 不必要的后台轮询。
- 网络请求。
- 通过额外常驻进程规避 Android 后台管理。

NotificationListenerService 属于通知接入所需的系统绑定机制，可以作为独立的必要组件进行验证。

# 十三、最终确认

本文件正式确认的核心规则：

2. 微信及其他应用通过 Android 通知监听机制接入。
3. 微信默认启用。
4. 其他应用由用户自主选择。
5. 只播报可读的消息类通知。

9. P0 为验证码短信。
10. P1 为其他所有消息。
11. P0 内部 FIFO。
12. P1 内部 FIFO。
13. P0 优先于等待中的 P1。
14. 正式采用方案 A：当前消息播完，再优先播报验证码。
15. 不采用普通消息暂停和恢复机制。
16. 独立安全事件可以立即停止播报。
17. V1.0 的音频、蓝牙、后台和全文安全限制继续继承。
