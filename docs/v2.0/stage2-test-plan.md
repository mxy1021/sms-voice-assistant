# V2.0 阶段2｜目标机操作单

验证设备为 vivo X200 Pro（V2405A），Android 17/API 37。以下步骤用真实受控微信发送者或测试群，准备一个短名称的测试联系人和群。回报只包含用例号、脱敏回调号、字段存在/长度、时间和人工听感。任何运行时授权、系统设置、重启、发送消息和操作微信均由用户完成。

## 1. 进入观察模式

1. 使用同签名 Debug APK 保留数据覆盖安装。若工程已通过 ADB 覆盖，直接打开原应用。核对原耳机目标、总开关、开机恢复、两规则、主题和增益，记作 N24 的配置证据。
2. 在主界面滚动到底部，依次点「开发诊断（阶段0历史工具）」和「微信通知技术验证」。确认探针显示本用户微信包 `com.tencent.mm`。
3. 点「打开系统通知使用权」，手动授权「微信通知技术验证（Debug）」，返回核对已授予、已连接及 `CONNECTED`（N01/N02）。若系统设置拒绝授权，记下原因并保留原限制。
4. 保持一次性语音未启用，按下表逐项发送或制造实际通知。观察 `POSTED` 与 `REMOVED`，不点击历史通知重放。对于可在通知栏/锁屏显示的样本，分别判断系统显示、应用字段和真实消息是否对应。

| 用例 | 操作与实证 |
|---|---|
| N03/N05/N06/N07/N11 | 应用阶段2页保持可见，测试联系人发一条短单聊。比较系统标题和正文与 `title/text/bigText/latestSender/latestText` 长度，确认是否为联系人而非应用标题或占位。 |
| N04/N05/N06/N07 | 短名称测试群发一条。核对 `conversation/group/latestSender` 与普通标题候选，注明系统是否明确给出群聊字段。 |
| N09 | 同一联系人连续两条不同长度，保持第一条通知在栏内。再从另一联系人发一条。比较 `notification/channel` 别名、postTime、`seenKey/samePostTime`、字段长度，观察原通知更新、两条并存或重复候选。相同键及时间无法单独证明正文相同。 |
| N08 | 临时关闭微信「通知显示消息详情」后发送一条，确认系统占位与监听字段。有合法无正文的通知时另记一条，记录缺正文与仅有占位的区别。恢复原预览设置。 |
| N10 | 由用户在可行时触发微信非消息通知，确认系统类型及应用类别/ongoing/summary。无法生成的项目保留 NOT_RUN。 |
| N09 补充 | 在系统中划掉测试通知，另测点开测试会话由微信自行撤掉通知，分别记录 `REMOVED` 和原因码。撤销通知和撤销授权是两个操作。 |

## 2. 接收时序和绑定恢复

| 用例 | 操作与实证 |
|---|---|
| N12 | 按 Home，确认主界面和探针页均不显示，再发新消息。返回后查该回调的 `importance`、可见标记和系统通知时间。 |
| N13 | 关闭屏幕发一条，随后另在已锁定的锁屏状态发一条。对照 `interactive/keyguard`、系统内容预览及监听字段。锁屏状态的“用户可见”单独记录。 |
| N14 | 离开页面且让手机静置，按实际场景记时长、USB、音乐、屏幕、系统后台配置。再发消息，查看接收回调。 |
| N15 | 由用户正常重启，首次解锁后不要打开本应用，直接发测试通知。应在打开应用前保留 `CONNECTED/POSTED` 的同一进程标识及时间。确认授权是否仍在。记录首次解锁、重启及发信时间。 |
| N16/N17 | 在原状态下先发一条确认监听，手动撤销通知使用权，再发一条，比较通知栏存在和探针有无事件。在系统重新授权，再发第三条，检查新连接与接收。撤权中若进程消失，只记录可观察结果。 |
| N02/N17 补充 | 授权仍在时，从页面点「测试一次系统解绑」。记录 `UNBIND_REQUEST`、实际 `DISCONNECTED/DESTROYED` 与解绑后投递。重新打开页面按需点「请求系统重新绑定」一次，观察 `CONNECTED` 及真实新消息。若系统自行重绑，单列系统行为。 |

`postToCallbackMs` 为设备墙钟下的系统通知发布时间差；微信远端发送时间另记，未测量时留空。`callbackElapsed` 与 `callbackToStartMs` 使用单调时钟。进程用 `run` 区分，同一次重启内才比较单调时钟。以实测报告范围和异常，暂不设强制毫秒阈值。

## 3. 音频、Android 17 和安全

1. 第一轮观察确认真实消息与字段之后，记下短信总开关原值，暂停短信播报。保持原指定耳机、增益、音量与厂商设置。先尝试断网固定语音，再由用户恢复微信测试所需的网络。离线候选与断网实际听验分别记录。
2. 在探针页点击「播放固定测试语音」（N18/N19/N20）。耳机听完整句，手机旁确认无语音。固定语音主观通过后点击页面确认按钮。固定前台失败时停留在音频排查，保留失败记录。
3. 分别进入前台、Home、屏幕关闭、已锁屏和后台静置测试。每次先点「下一条测试通知：固定句」或「下一条测试通知：真实字段」，再进入该场景，让受控联系人或群发**完全相同的约定句「测试语音。」**（无需引号）。一次性许可最多10分钟，收到符合选文条件的新回调即清除。背景测点以 `AUDIO_FOCUS` 的可见性、交互和 importance 为准。只有固定语音基线通过才测试真实字段语音。
4. 音乐分别做有/无音乐对照（N21），记焦点结果、是否完整、音乐是否降低并恢复、手机与其他设备有无语音。按需测试目标耳机断开（N23）、授权撤销、另一蓝牙设备连接但目标耳机断开，以及焦点永久丢失。观察取消、释放与下一次恢复监听时有无旧语音。设备已无声的案例仍须区分主动拒绝与音频框架拦截。
5. 读取应用脱敏日志与未经修改的音频系统日志（N22）。焦点拒绝时记录层级；如果该轮未创建 AudioTrack，填该轮实际发声测试不可达。Track 标记或写入字节数只是 API 指标。当前系统保护配置保持原样。
6. 取消一次性实验并恢复短信总开关原值。在监听已连接且只观察时发送受控 SMS 与微信通知，至少验证同时到来时微信只有观察、SMS 在耳机正常播放。核对四组合及0/+3/+6/+9、三个主题、原5条等待预算、短信总开关和重启配置。测试所需短验证码采用用户控制的测试样本。原 URL 运营商拦截的历史证据单独保留。

## 4. 只读排查与反馈

```powershell
adb -d logcat -d -s SVA_STAGE2:I
pwsh -NoProfile -File scripts/Read-AudioHardening.ps1 -SinceEpochMillis <本轮开始毫秒>
```

只摘录本应用阶段2脱敏行与过滤后的 AudioHardening 标量。使用同一组 `run`、`callback` 将 `POSTED`、`AUDIO_SELECTION`、`AUDIO_FOCUS` 和 `AUDIO_END` 对齐。重启/脱离 USB 场景先让系统产生真实事件，再重连仅采集日志。若用户尚未操作，对应真机项为 NOT_RUN。

反馈示例：N03，前台，收到，回调号 3，标题长度和测试联系人相符，正文有，应用未提供结构化发送者。N22，Home，回调号 8，耳机未听到，未观察到手机语音，音乐未降低。无需回传微信或短信内容。
